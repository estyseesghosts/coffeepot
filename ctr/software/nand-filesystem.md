# CTR NAND filesystem

The 3DS keeps its system software, settings and built-in apps on a soldered flash chip (**[eMMC](../../glossary.md#emmc)** [NAND](../../glossary.md#nand)). Everything on it is encrypted with keys tied to that console. Inside it is a small partition table and a handful of [FAT](../../glossary.md#fat) filesystems — some for 3DS mode, some for the Nintendo DSi mode the console also supports.

Users never see this chip directly; the operating system exposes pieces of it to programs through filesystem services, and only a few directories are open to normal apps.

## Behavior

The NAND holds: the [firmware partitions](firmware.md) (`firm0` and `firm1`), the 3DS system filesystem (called **CTR-NAND**, volume label `CTR`), a DSi-mode filesystem (`twln`) plus a photo partition (`twlp`), and an optional Game Boy Advance save area. System titles and system save data live in CTR-NAND, in clear text — only the NAND as a whole is encrypted.

Normal ARM11 programs cannot reach any of this except the `twlp` photo partition and a small set of directories (for example `nand:/rw/`). Access to CTR-NAND or TWL-NAND from the ARM11 needs special exheader access flags that retail processes never get. Everything else goes through [Process9](os.md) on the ARM9.

## Technical details

### Sizes and encryption

The chip varies by vendor (see [models](../hardware/models.md)), but the firmware always uses the same partition table sizes: `0x3AF00000` bytes (**943 MiB**) on Old 3DS and `0x4D800000` bytes (**1240 MiB**) on New 3DS. A bigger chip leaves the rest unused. 3dbrew's physical-size list [documented: 3dbrew Flash Filesystem]:

| Device | Maker | Chip size |
| ------ | ----- | --------- |
| Old 3DS / 2DS | Toshiba | `0x3AF00000` |
| Old 3DS / 2DS | Samsung | `0x3BA00000` |
| New 3DS | Toshiba | `0x76000000` |
| New 3DS | Samsung | `0x4D800000` and `0x74800000` (both listed) |

3dbrew's list also gives `0x76000000` (Toshiba) and `0x4D800000` (Samsung) rows labelled "2DS" next to the `0x3AF00000` and `0x3BA00000` rows.

> Unknown: the source does not say which device those larger "2DS" rows are (the New 2DS XL is a likely but unconfirmed candidate, since it uses the New 3DS partition size).

| Property | Value |
| -------- | ----- |
| Cipher | AES-CTR |
| TWL regions | TWL NAND keyslot; counter nonce is the byte-reversed SHA-1 of the NAND CID. The first `0x0B100000` bytes use the TWL key, but before `0x00012E00` only the MBR partition table is encrypted |
| CTR regions | CTR NAND keyslots (separate keys for Old and New 3DS); nonce is the SHA-256 of the NAND CID. The keyslot per partition is set by the NCSD partition FS type and encryption type |
| Never-written sectors | plaintext `0x00` or `0xFF` |

A NAND image cannot simply be re-encrypted and used on another console: some files in the `nand` partition are console-specific.

### Layout (Old 3DS | New 3DS)

| Offset | Size | Name | Description |
| ------ | ---- | ---- | ----------- |
| `0x0` | `0x200` | | NCSD header with the CTR partition offsets/sizes; also holds the TWL MBR partition table |
| `0x00000000` | `0x0B100000` | | TWL NAND region (NCSD index 0, key slot `0x03`) |
| `0x00012C00` | `0x200` | | New 3DS only: console-unique encrypted key store |
| `0x00012E00` | `0x08FB5200` | `twln` | DSi FAT16 filesystem |
| `0x09011A00` | `0x020B6600` | `twlp` | DSi photo FAT12 filesystem |
| `0x0B100000` | `0x30000` | | AGB_FIRM GBA savegame (empty if `AGB_FIRM` was never run), key slot `0x07` |
| `0x0B130000` | `0x400000` | `firm0` | Firmware (key slot `0x06`) |
| `0x0B530000` | `0x400000` | `firm1` | Backup firmware |
| `0x0B930000` | `0x2F5D0000` (Old) / `0x41ED0000` (New) | | CTR-NAND partition; NCSD FS type `0x01`, index 4, encryption type `0x02` (Old) or `0x03` (New); key slot `0x04` (Old) or `0x05` (New) |
| `0x0B95CA00` (Old) / `0x0B95AE00` (New) | `0x2F3E3600` / `0x41D2D200` | `nand` | CTR FAT16 filesystem |

NCSD partition details: TWL region FS type `0x01`, encryption `0x01`, index 0; AGB save FS type `0x04`, encryption `0x02`, index 1; `firm0` FS type `0x03`, encryption `0x02`, index 2; `firm1` index 3. TWL FAT volumes are named `TWL`, CTR volumes `CTR`. TWL partition offsets come from the MBR; CTR ones from the NCSD header. Sector 0 of the CTR-NAND partition holds an MBR for the `nand` FAT16 volume (signature at `+0x1FE`). The New 3DS CTR-NAND uses a keyslot separate from Old 3DS.

On some systems (3dbrew names the 3DS XL) there is a plaintext FAT16 boot record at `0x4000`; it does not exist on launch-day systems and is the only plaintext block. The New 3DS key store at `0x12C00` (0x200 bytes, AES-ECB) is encrypted with a console-unique keyX+keyY generated by the New 3DS arm9bin loader (then cleared) and AES-ECB; its plaintext is identical on all retail New 3DS units (and, differently, on all dev units). Layout: `0x0` (`0x10`) normal-key for key slot `0x11`, used to derive the other New 3DS keyXs; from 9.6.0-X this one only produces slots `0x15` and `0x18`; `0x10` (`0x10`) second slot-`0x11` normal-key from 9.6.0-X for slots `0x16` and `0x19`-`0x1F`; `0x20` (`0x1E0`) unused as of 9.6.0-X. See [system flaws](system-flaws.md) for the weaknesses.

### CTR-NAND directory tree

```text
nand
├── __journal.nn_
├── data/<ID0>/{extdata, sysdata}   # cleartext; ID0 = SHA-256 hash of movable.sed keyY
├── dbs/                             # title database
├── fixdata/sysdata
├── private/movable.sed
├── ro/   (nandro archive)
│   └── sys/{HWCAL0.dat, HWCAL1.dat}
├── rw/   (nandrw archive)
│   └── sys/{lgy.log, LocalFriendCodeSeed_B, native.log, rand_seed, SecureInfo_A, updater.log}
├── ticket/                          # empty: tickets are in ticket.db
├── title/                           # same structure as the SD card title directory
└── tmp/
```

`nand/data/<ID0>/extdata` holds shared extdata, structured like SD extdata. System titles' save data is stored under `nand/data/<ID0>/sysdata` (not beside the title as on SD). The `movable.sed` key Y is used only for AES MACs here. `native.log` is written by the error display; `lgy.log` by `TWL_FIRM`.

> Conflict: 3dbrew's NAND page says in one sentence that the ARM11 can reach `nand:/rw/` mounted as the `nandrw` archive and `nand:/ro/` as `nandro`, and a few lines later that the `ro` and `rw` directories are accessible through `nandrw` and `nandro` "respectively" (the reverse pairing). This page follows the first statement (`rw` = `nandrw`, `ro` = `nandro`). Contents: `ro` has `private`, `shared` and `sys/{HWCAL0.dat, HWCAL1.dat}`; `rw` has `shared` and `sys/...` as in the tree above. None of the NAND partitions are normally reachable from the ARM11 except `twlp`; CTR/TWL NAND access needs exheader access descriptors that retail ARM11 processes never have.

### TWL partition

Mostly the same as a DSi's, except tickets are stored in the CTR FAT filesystem; the `twln/title` structure mirrors the CTR layout but the `.cmd` file is cleartext (probably a dummy), and DSi directory names use the DSi's title-ID high words. The `twln` tree is `import`, `shared1`, `shared2/0000`, `sys/{TWLFontTable.dat, log/inspect.log, log/product.log}`, `ticket`, `title`, `tmp`; `twlp` holds `photo`. The system title `data` directory does not exist (probably DSiWare only). The `nand/tmp` directory is usually empty even when a system update still needs finalising.

## Homebrew notes

Reading the chip needs its pinout (documented on 3dbrew) and keys from [OTP](../hardware/security-hardware.md); NAND dumping and "redirection to SD card" were key steps in the history of [custom firmware](../homebrew/custom-firmware.md) (the emuNAND concept). Tools like GodMode9 browse NAND once a console has [ARM9 access](../homebrew/boot9strap.md).
