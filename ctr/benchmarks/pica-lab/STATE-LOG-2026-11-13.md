## 1. What we did

1. **Automation (v0.2).** SELECT runs all six families in one launch: selftest, raster+edge, tev, blend, perf, probe. A failed self-test or any error aborts the sequence. A, B, X, Y, L, R still run single families.
2. **Run folders and logs.**
   - Each launch creates `sdmc:/3ds/pica-lab/run_NNN/` (the app now makes `/3ds/pica-lab` itself).
   - It contains `run.log` (timestamped, flushed per line), `results.csv`, `manifest.txt` and `probe.txt`.
3. **Edge and perf repair (v0.3).**
   - Edge: each triangle now gets its own vertex slots.
   - Added the `edge_cov` family, which uses additive coverage.
   - Perf was redesigned (section 4).
   - `results.csv` gained a `p3d_us` column.
4. **One zip per run.**
   - `run_NNN.zip` is uncompressed (STORE) and holds the `.rgba` dumps plus the text files, which are added at clean exit.
   - The central directory is rewritten every 32 entries and after each family.
   - Each entry's data is padded to start on a 512-byte boundary.
5. **Host tools.**
   - `analyze.py` and `interrogate.py` accept `.zip`, a run folder or `results.csv`.
   - They report `edge_cov` gaps and overlaps.
   - The perf report shows deltas against `empty`.
6. **Reading list.** Before changing the code we read `coffeepot/ctr/benchmarks/drawbench`, `engineering/performance.md` (citro3d timers, GSP perf log) and the benchmarks README.

## 2. Assumptions we were right about

- Self-test passes. Results are bit-identical across separate launches (207 of 207 non-perf hashes, 3 launches). Forward and reverse raster sweeps give identical images.
- Blend and TEV follow the expected arithmetic to about 1 LSB. TEV steps by 8 per step on red.
- The edge test was broken by the harness, not the GPU. Reusing vertex slots made the second triangle draw twice, giving half coverage (8224 and 8256 of 16384 px).
- After the fix, both diagonals give identical 16384 px images, and all 40 additive coverage cases are watertight (0 gaps, 0 overlaps), including the 4-triangle fan with slanted shared edges.
- The old perf null (0.414 ms for both 1 and 64 draws) was a measurement floor, not proof that draws are free.
- GPU-side draw count costs nothing measurable: 768 triangles take 420–423 µs in 1, 16, 64 or 256 draws. The CPU-side cost (about 9.6 µs per draw in citro3d) is separate and not measured here.
- `GSPGPU_ReadHWRegs` is readable from homebrew.

## 3. What we were wrong about

- **"1/4-pixel snap grid."** This was my hypothesis after the first runs, and it is retracted.
  - Raster transitions at steps 9, 25, 41 and 57 are where a 3:4-slope hypotenuse crosses pixel centers (offsets 1/8 + k/4, plus one step for the tie).
  - The vertical edge flips at step 32 (offset 0.5).
  - Both fit an exact pixel-center rasterizer with ties counted outside. We see no evidence of coarse snapping at 1/64 resolution. Finer quantization is not ruled out.
- **FNV-1a as an image identity.** Two images differing in 768 bytes shared hash `45949DC5` (edge_cov cases 133 and 139). Only one such pair existed in the run, but the CSV hash must not be trusted. Verify with SHA-1 of the `.rgba`.
- **Seek-back zip index as the stall cause.** Wrong. The real cause was unaligned writes.
  - Entries were 262,198 bytes, so every second entry's data started at an offset that is not a multiple of 4, and each of those writes took about 10 s.
  - Padding the local header so data starts on a 512-byte boundary fixed it (raster+edge now takes 28–32 s).
  - This is an inference from the alternating pattern and the fix working. Not isolated further.
- **The old perf baseline.** The first perf test measured the clear plus a 235 µs floor, not the draws.
- **README.** It still says "one family per launch" and "`.rgba` files on the SD card". Both are now wrong.
- **Procedural.** Python in heredocs through the shell tool lost one level of backslashes, so earlier scripted edits of `main.c` failed. Use the Edit tool for C source.

## 2026-11-14 update 3: runs 015-017 (v0.6), the synchronisation fault, v0.7

Prompted by an external audit of `d2193bf` (private notes, 2026-11-14), checked against the pinned citro3d `9f21cf7` and libctru `62b7c42` sources and the run data.

### Synchronisation fault (all timed families, v0.4-v0.6)

- `perf_frame` and `p2_frame` read the perf log and `C3D_GetDrawingTime()` after `C3D_FrameEnd(0); C3D_FrameSync();`. `C3D_FrameSync` (`renderqueue.c` 75-85) loops on `gspWaitForAnyEvent()` until both VBlank frame counters change; it does not wait for the GX queue. The queue wait is `C3Di_WaitAndClearQueue` inside `C3D_FrameBegin` (163-176). So a sample was only associated with its frame if the GPU happened to finish before the next VBlank, and nothing checked that.
- v0.6 `timing_wall` (FrameEnd..FrameSync) therefore timed the VBlank wait: 16.3-16.6 ms in every variant of runs 015-017, whatever the GPU work.
- `C3D_GetCmdBufUsage()` was read before `C3D_FrameEnd`, and `C3Di_SplitFrame` updates it, so the cmdbuf warning described the previous frame.
- The "empty" variant recorded no GPU command, so `C3Di_SplitFrame` returned "nothing was drawn" (`base.c` 313-314), nothing was submitted, P3D read 0, and `C3D_GetDrawingTime` repeated an earlier frame's value. In v0.3 perf the empty frame read 0.235 ms, the same as `tri192_d1`; in runs 003 and 015, 39 of 40 empty readings are bit-identical to the previously logged frame's. **The "235 µs drawing-time floor" in section 4 was this artefact.** Every non-empty perf variant read P3D + 143-149 µs, with no floor.
- Image families are unaffected: `capture()` uses `C3D_SyncDisplayTransfer`, which waits for the queue before reading back.

### What runs 015-017 show

- 2403 cases each, 0 errors. All 753 captures byte-identical across the three runs (`analyze.py compare`); the 597 cases shared with run 012 have identical CRCs.
- `raster_fine`: 0 differing steps in all 21 windows, forward and reverse. The inward-normal tie rule fitted to runs 009-012 predicted the three untested classes, and C1-C6 confirmed all three: (-,0) 256 covered / 0, (0,-) 0 / 192, (+,+) 128 / 0. Evidence level moves from "reproduced" to "predicted and confirmed" for those classes; still one console, one firmware, one 256x256 RGBA8 target.
- **Readback orientation checked with an asymmetric shape:** `raster` step 0 (legs 96 px along program x, 128 px along program y) covers raw rows 80-175 and raw columns 48-174, right angle at the low corner. Raw word index of program (x, y) is `x*256+y`; `rasterfine.py` already used this, the 2026-11-13 note and the GPU wiki page had `y*256+x`.
- P3D anomaly: every rep of s3 n = 1, 16, 64, 256 (and pitch 8); never for s8, never for any repeated-draw variant; s3_n512 twice in 120 reps (run 016, `_gap`). P3D 50.0-183.8 ms; normal P3D 28-1284 us. Anomalous `_blk` cases are 83-111 ms apart in `run.log` against 67-69 ms for normal ones: real extra wall time of about 16-44 ms, less than P3D claims. ### v0.7 (builds, -Wall -Wextra clean, not run)

- `timed_begin`/`timed_end` shared by perf, perf2 and timing_iso. Order: `C3D_FrameBegin(SYNCDRAW)` (timed as `begin_us`, outside every GPU interval), draws, perf log p0, `C3D_FrameEnd(0)` (`frameend_us`), `gxCmdQueueWait` until the queue is idle (`drain_us`), perf log p1 (`perflog_us`), then drawing time and cmdbuf usage for this frame. `gxCmdQueueWait` ignores its queue argument at the pinned libctru (`gxqueue.c` 107-119), so NULL is passed.
